> 微信客户端锁哪个版本、适配层现在依赖什么、大模型花不花钱、环境怎么核对。
>
> 第一节的实测结论来自 2026-09-07 在 Windows 11 虚拟机上的实测，每条都附证据；
> 第二节是适配层 `wxui` 的依赖、许可与能力边界。
> 不是"应该"、不是"据说"——写不出证据的结论没写进来。

> **这里的「免费/付费」只指大模型（第三节）。**

## 一、先看这一条：只有微信 4.1.8.107 能用

**微信客户端版本必须锁死在 `4.1.8.107`，并且必须堵死自动更新。**

| 微信版本 | 能不能用 | 判定依据 |
|---|---|---|
| **4.1.8.107** | ✅ **唯一可用** | `WM_GETOBJECT` 返回 `49275`，UIA 控件树完整 |
| 4.1.13.12 | ❌ 完全不可用 | `WM_GETOBJECT` 返回 **`0`**，UIA 控件树**空** |
| 3.9.12.17 | ❌ 登录被拒 | 腾讯服务端判「微信版本过低」，客户端侧无法绕过 |

### 4.1.13.12 为什么完全没救

**它没有实现无障碍（Accessibility）接口。** 这不是代码的问题——本项目用的 `uiautomation`
以及所有界面自动化方案，**全都建立在 Windows UI Automation 之上**，
这个版本不给 UIA 任何东西，所以**换任何实现都没用**。

同一台机器上的 A/B 对照：

```
微信 4.1.13.12
  主窗口 ClassName = 'Qt51514QWindowIcon'（两个同名顶层窗口，同一 pid）
  SendMessageW(hwnd, WM_GETOBJECT, 0, OBJID_CLIENT)
      hwnd=197498 -> 0        # 0 = 没有 IAccessible / UIA 提供者
      hwnd=197526 -> 0
  UIA 树：WindowControl(Name='微信') -> PaneControl(Name='Weixin') -> 到底，零子控件

微信 4.1.8.107
  主窗口 ClassName = 'Qt51514QWindowIcon'（同一个类名！）
  SendMessageW(hwnd, WM_GETOBJECT, 0, OBJID_CLIENT)
      hwnd=328140 -> 49275    # 非 0 = 有无障碍提供者
  UIA 树：
      WindowControl(Name='微信')
        └ GroupControl(Class='QWidget')
            ├ CustomControl(Class='QStackedWidget')
            │   └ GroupControl(Class='mmui::MainView')
            ├ ToolBarControl(Class='mmui::TitleBar')
            │   ├ ButtonControl(Name='置顶')
            │   ├ ButtonControl(Name='最小化')
            │   ├ ButtonControl(Name='最大化')
            │   └ ButtonControl(Name='关闭')
            └ GroupControl(Class='QWidget')
```

读消息要用的会话列表、消息列表这些控件，在 4.1.13.12 上一个都拿不到。
wxui 连接时会先做这个判定，直接报：

```
AccessibilityUnavailable: 微信窗口没有实现无障碍接口（WM_GETOBJECT 返回 0）。
实测微信 4.1.13 及以上是这种情况，界面自动化完全读不到内容，只能改用受支持的微信版本。
```

### 排掉的三个错误假设

排查时最容易在这三个方向上白费一整轮，都验过了：

| 假设 | 实测结论 |
|---|---|
| 类名变了、版本号对不上 | **不成立**。4.1.13.12 和 4.1.8.107 的主窗口类名**完全一致**，都是 `Qt51514QWindowIcon`（见上面 A/B 对照） |
| 微信没登录 / 主窗口被关了 | **不成立**。截图确认登录着，会话列表、目标群都正常显示 |
| 微信刚启动的竞态 | **不成立**。等窗口完全就绪后重试，一样失败 |

### 排查手法（记住这一条能省一整轮）

遇到「连不上微信」，**先发 `WM_GETOBJECT` 判定是"找不到窗口"还是
"窗口里根本没有控件树"**——两者的出路完全不同（wxui 连接时已经自动做了这一步：
前者抛 `WeChatNotRunning`，后者抛 `AccessibilityUnavailable`）：

- 找不到窗口 → 检查窗口是否可见、是否登录、要不要 `-interactive`
- 窗口里没控件树 → **只能换微信版本**，在代码上折腾全是白费

```python
import ctypes
from ctypes import wintypes
u32 = ctypes.windll.user32
OBJID_CLIENT = 0xFFFFFFFC
r = u32.SendMessageW(hwnd, 0x003D, 0, ctypes.c_long(OBJID_CLIENT).value)
print(r)   # 0 = 这个微信版本没救，非 0 = 有无障碍接口
```

### 3.9.12.17 为什么也不行

装是能装上（`WeChatSetup-3.9.12.17.exe` 静默 `/S` 安装正常），
但**登录时被腾讯服务端拒绝，提示「微信版本过低」**。

这是服务端校验，**客户端侧没有合法手段绕过**。同系列更新的 3.9.12.45/.51/.55/.57
大概率同样被拒（都是 3.9 系），且需要从外部下载安装包，不推荐再试。

### 必须堵死自动更新（不做等于白干）

**这台机器就是这么坏的：9/4 装好 4.1.8.107，之后微信自己升到 4.1.13.12，整条链路作废。**

更新器路径带版本号子目录：

```
C:\Program Files\Tencent\Weixin\<版本号>\WeixinUpdate.exe
```

⚠️ **只改名不够**——升级时微信会在**新版本子目录**里重新生成一个，等于没堵。
有效做法（三层，实测有效）：

1. `WeixinUpdate.exe` 改名成 `WeixinUpdate.exe.bak`（保留，便于还原）
2. **在原路径创建一个同名的「目录」占位**——文件和目录不能同名，微信再也生成不回来
3. 加防火墙出站拦截规则

**并且要实测验证，不能设置完就宣布成功：**

```powershell
# 路径里有 [ ] 方括号，PowerShell 的 -Path 会当通配符，必须用 .NET 方法
[System.IO.Directory]::CreateDirectory($upd)

# 实测能不能写回去 —— 这一步才是验收
try   { [System.IO.File]::WriteAllBytes($upd, [byte[]](1,2,3)); "!! 占位没生效" }
catch { "写回被拒绝【符合预期】" }
```

**时机很重要：装完微信后、第一次启动微信之前就要堵。** 上一次就是装完先启动，
被它自己升掉了。

## 二、适配层：wxui

读写微信这一层由项目自带的 `wxui/` 实现：找窗口、切会话、读消息、发消息。

### 依赖与许可

| 依赖 | 许可 | 用途 |
|---|---|---|
| `uiautomation` | Apache-2.0 | Windows UI Automation 封装，唯一的界面依赖 |
| `requests` | Apache-2.0 | AI 接口 / 后端 HTTP 调用 |
| `pymysql`（可选） | MIT | 直连 MySQL 时才需要 |

**全部是宽松开源许可，允许商用、分发和转售，没有任何第三方付费授权环节。**

### 能做什么、不能做什么

面向客户的说法在 [`../README.md`](../README.md) 的「能做什么 · 不能做什么」，
<!-- 维护视角的已知局限在 [`内部维护说明.md`](内部维护说明.md) 第四节。 -->
这里只说边界从哪来 —— **边界的来源不同，能不能解决也不同**。

### 哪些限制是微信侧的：换任何实现都在

| 限制 | 根因 | 能不能解决 |
|---|---|---|
| 微信 4.1.13+ 完全用不了 | 客户端没有实现无障碍接口（见第一节 `WM_GETOBJECT` 返回 `0`） | **不能**。只能锁版本 |
| 发送前无法确认 @ 到了谁 | 微信的 @ 要从候选列表里挑人，界面自动化拿不到可靠的群成员表 | **不能**。所以刻意不做 @，改在正文里带称呼 |
| 多条消息同一瞬间到达时只有最后一条能拿到昵称 | 昵称来自会话摘要，刷新比消息本身慢 | 只能缓解（已加短重试 + 按 id 缓存），不能根除 |

### 多群：还没做

- `bot.py` 目前只盯 `LISTEN_GROUPS` 的**第一个**群；配了多个，启动时会打 warning 并忽略其余
- 原因：所有会话共用同一个微信主窗口，同时盯两个群，轮询时会互相把对方切走
- 要做多群，方向是独立聊天子窗口，或单线程按固定节奏轮流切会话。工作量是自己的开发成本

### 踩过的坑

**① 不抛异常 ≠ 成功**

同一类问题出现过多次：接口返回了失败结果却不抛异常、切到会话后读到 0 条却没有任何报错、
AI 接口返回 HTTP 200 但 `content` 是空串。
**凡是返回值能表示失败的接口，必须接返回值再判定**，别只用 try/except 兜。

**② 切会话要校验，别信"没报错"**

早期出现过：切换会话的调用正常返回，但主窗口右侧仍是空白默认页，读消息恒为 0 条。
**原因没有定位到**，别把任何一种猜测当成已证实的因果。

现在的做法是切完用 `ChatInfo()` 核对会话名、不一致就重试（`bot.py` 的 `MessageStream.acquire()`），
轮询时每轮也校验（`_on_target_chat()`），人手动点走或弹窗抢焦点都能自动切回。问题没有再复现。

## 三、大模型：免费 vs 付费

### 结论：智谱 GLM 的 Flash 系列是唯一真正「不限量」的

| 平台 | 免费程度 | 适不适合 |
|---|---|---|
| **智谱 GLM-4-Flash / 4.7-Flash** | **永久免费、不限总量**，限制只在并发 | ✅ **首选** |
| 硅基流动 SiliconFlow | ¥14 赠金 + 部分小模型永久免费 | 🟡 备用（走 `custom` 预设） |
| 通义千问 | 新用户 100 万 token / 90 天 | ❌ 会过期 |
| 百度文心 ernie-speed / ernie-lite | 官方公告长期免费 | 🟡 备用（有 `baidu` 预设） |
| OpenRouter | 300+ 模型有 free tier | ❌ 国外，虚拟机网络不稳 |

> **赠送额度 ≠ 免费模型**。新用户送的额度是抵扣**付费**模型的；
> Flash 是独立的免费档，不消耗额度、也不会用完。

### 免费档的三个坑

**坑 1：两种 429 完全不同，别混为一谈**

| 错误码 | 含义 | 归属 | 怎么办 |
|---|---|---|---|
| `1302` | 您的账户已达到速率限制 | **我们打太密** | 降低频率 / 退避重试 |
| `1305` | 该模型当前访问量过大 | **免费池被全网挤爆，与我们无关** | 换模型 / 切备用通道，重试没用 |

混淆的代价：一直往自己身上找原因，改超时、改重试全是白费。
（实测：`requests` 和 `curl` 对 `1305` 返回完全一致，说明与客户端无关。）

**坑 2：推理模型会把 `max_tokens` 吃光，`content` 返回空但 HTTP 仍是 200**

`glm-4.7-flash` 是推理模型。实测 `max_tokens=64`：

```
默认设置                → finish_reason='length'  content=''  reasoning_tokens=64
thinking:{"type":"disabled"} → finish_reason='stop'  content='在的，我看了一下…'  reasoning_tokens=0
                              且总消耗从 64 降到 14
```

表现是「AI 调用成功、日志一片正常、机器人就是不吭声」。

两处修法都做了：
- `ai_provider.py` 按「厂商 + 模型名」双重判定后自动加 `thinking:{"type":"disabled"}`
  （别的厂商传了会 400，所以不能无脑加）
- **把「content 为空」改判为失败**并打印 `finish_reason` / `reasoning_tokens`，
  下次遇到直接能从日志看出原因

**坑 3：模型选型——新的不一定更可用**

| 模型 | 2026-09-07 实测 |
|---|---|
| `glm-4-flash-250414` | ✅ HTTP 200 / **0.24s** / 4 个 completion token / **非推理模型** |
| `glm-4.7-flash` | ❌ 持续 `429 / 1305 访问量过大` |

所以**主力用 `glm-4-flash-250414`**（快、当前可用、非推理更适合群聊短回复），
`glm-4.7-flash` 降为**备用**（更强，闲时顶上）。**同一把 key，不用另外注册。**

`AIEngine` 会按 `providers` 顺序逐个试、第一个成功就返回，所以主力被挤爆时自动切换。

### 密钥放哪

**绝对不要写进 `config.py`——那是要进版本库的。**

复制 `settings.example.json` 成 `settings.json`（已在 `.gitignore` 里），在那边写：

```json
{
  "DRY_RUN": false,
  "AI": {
    "enabled": true,
    "providers": [
      {"preset": "zhipu", "api_key": "你的key", "model": "glm-4-flash-250414"},
      {"preset": "zhipu", "api_key": "你的key", "model": "glm-4.7-flash"}
    ]
  }
}
```

`settings.json` 里写了什么就覆盖 `config.py` 里的什么，没写的沿用默认值。

拿 key：https://www.bigmodel.cn/usercenter/proj-mgmt/apikeys （注册即用，不用绑卡）

单独验 key 通不通（**先验再接，别让一轮测试白跑**）：

```
python ai_provider.py zhipu 你的KEY
```

## 四、三层回复决策链的成本分布

| 层 | 触发条件 | 成本 | 需要什么 |
|---|---|---|---|
| 1. 业务指令 | 命中 `handlers.py` 里注册的指令 | 零 | 要连数据库 / 后端 |
| 2. 关键词规则 | 命中 `RULES` 里的关键词 | **零** | 什么都不用，开箱可用 |
| 3. AI 兜底 | 默认**仅被 @ 时** | 免费档下为零 | 需要 API key |

**为什么业务指令必须排在 AI 前面**：订单号、库存、余额这类数据只能来自数据库，
交给 AI 它就会编。AI 只管闲聊。

**为什么 `only_when_at_me` 建议保持 `True`**：群里每句话都喂给 AI，
在 1 QPS 的免费档下会持续排队/限流，而且很吵。

三层都没命中时 `FALLBACK_REPLY = None` → 不吭声。**这是设计如此，不是故障。**

## 五、环境锁定清单

配好之后按这个清单核对，任何一项不符都会出问题：

- [ ] 微信客户端 = **4.1.8.107**（`Weixin.exe` 属性里看文件版本）
- [ ] 自动更新已堵死，且**实测过写回 exe 被拒绝**
- [ ] `pip show uiautomation` → 有版本号（**≥ 2.0.29**）
- [ ] Python 3.12
- [ ] Windows **已登录的交互式桌面**（有 `explorer.exe`、**没有** `LogonUI.exe`）
- [ ] 已配自动登录，否则重启/挂起恢复后机器人起不来
- [ ] 显示器/待机/休眠超时 = 从不（`powercfg /change monitor-timeout-ac 0`）
- [ ] 微信主窗口开着、别最小化
- [ ] `settings.json` 已建且**不在版本库里**
- [ ] `config.py` 里 `api_key` 是空的

> 息屏本身**不影响** UIA 读取（实测息屏状态下 1213 次轮询、0 读取错误），
> 但关掉更省心。
